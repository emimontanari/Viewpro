# Stage 22.4 — Team Invitation Acceptance Design

Stage 22.4 completes the team invitation lifecycle started in Stage 22.2 and surfaced in Stage 22.3. Managers can already create a manual invitation link. This slice lets the invited person open that link, prove they own the invited email, join the invited tenant, and receive an authenticated session.

## Decision

Build a **dedicated public team invitation acceptance flow** with a separate public backend controller and an invite-specific app-new page.

| Option | Decision | Why |
|---|---|---|
| Public `team-invitations` controller + invite page | Accepted | Keeps public token endpoints separate from guarded `/team/*` management endpoints and matches the URL contract already generated by Stage 22.2/22.3. |
| Redirect existing users through normal sign-in | Rejected for this slice | The current sign-in redirect allowlist does not include invitation URLs, and putting raw invitation tokens in generic auth redirects increases leakage/history risk. |
| Password-only acceptance for every existing user | Rejected as the only path | Secure but worse UX for users who are already logged in with the invited email. |

Approved existing-user behavior: support **both** paths:

1. If the user is already logged in with the invited email, they can accept directly.
2. If they are not logged in, they can enter the existing account password on the invitation page.

## Scope

Included:

- Add public backend endpoints:
  - `GET /team-invitations/:token`
  - `POST /team-invitations/:token/accept`
- Validate invitation tokens by hashing the raw token server-side.
- Return safe invitation metadata only:
  - invited email;
  - role;
  - tenant name/slug/status;
  - expiry;
  - whether the invited email is already registered.
- Accept invitations for brand-new users:
  - create active `User`;
  - create `TenantMembership` for the invited tenant/role;
  - mark invitation `ACCEPTED` with `acceptedAt`;
  - create auth cookies and return a normal session response.
- Accept invitations for existing global users with no membership in the invited tenant:
  - already-logged-in same-email path;
  - password verification path;
  - create only the missing `TenantMembership`;
  - mark invitation accepted;
  - return an authenticated session with memberships.
- Add the public app-new route:
  - `/team-invitations/[token]`
- Add a focused team invitation acceptance UI with Spanish copy.
- Add targeted backend and app-new tests.

Not included:

- Email delivery.
- Pending invitations list.
- Resend/revoke UI.
- Bulk Excel/CSV invitation import.
- Role changes for active members.
- Member deactivation/suspension.
- Trial/user-limit enforcement.
- Generic auth redirect changes for invitation links.
- PR creation, commits, or branch cleanup without explicit user confirmation.

## Backend architecture

Keep the existing private team management controller unchanged in purpose:

```txt
/team/*
  AuthGuard + TenantMembershipGuard + PermissionGuard
  create/resend/revoke/list team management actions
```

Add a separate public controller:

```txt
/team-invitations/*
  public token validation and acceptance endpoints
  accept endpoint protected by AuthThrottlerGuard
```

Recommended file:

```txt
viewpro-app/apps/api/src/team/team-invitations-public.controller.ts
```

This avoids weakening the class-level guards currently protecting `TeamController`.

### Public endpoint contract

#### Validate invitation

```txt
GET /team-invitations/:token
```

Response:

```ts
type TeamInvitationPublicResponse = {
  email: string;
  role: 'MANAGER' | 'AGENT';
  status: 'PENDING';
  expiresAt: string;
  emailRegistered: boolean;
  tenant: {
    id: string;
    name: string;
    slug: string;
    status: string;
  };
};
```

Rules:

- Hash raw token with `hashTeamInvitationToken()`.
- Return `404` for unknown token.
- Return `410` for expired, revoked, or accepted invitations.
- Do not return invitation id, raw token, or token hash.
- `emailRegistered` is allowed because only a valid token holder can see this metadata.

#### Accept invitation

```txt
POST /team-invitations/:token/accept
```

Request DTO:

```ts
type AcceptTeamInvitationDto =
  | {
      mode: 'register';
      firstName: string;
      lastName?: string;
      password: string;
    }
  | {
      mode: 'login';
      password: string;
    }
  | {
      mode: 'current-session';
    };
```

Response: same shape as `MeResponse` from `/auth/me`, with auth cookies set on the response.

Rules:

- `register` is only for emails that do not already exist.
- `login` verifies the existing account password for the invitation email.
- `current-session` requires a valid access-token cookie and the cookie user email must match the invitation email.
- A logged-in user with a different email cannot accept the invitation.
- If the invited user is already a member of the tenant, return a safe conflict/gone response and do not mutate the invitation.

## Repository/use-case design

Extend `TeamInvitationsRepository` with token validation and acceptance operations. Keep token hashing in the use case/controller boundary so the repository receives `tokenHash`, never raw token.

Suggested repository results:

```ts
type ValidateTeamInvitationResult =
  | { status: 'valid'; invitation: TeamInvitationWithTenant; emailRegistered: boolean }
  | { status: 'notFound' }
  | { status: 'expired' }
  | { status: 'revoked' }
  | { status: 'alreadyAccepted' };

type AcceptTeamInvitationResult =
  | { status: 'accepted'; user: User }
  | { status: 'notFound' }
  | { status: 'expired' }
  | { status: 'revoked' }
  | { status: 'alreadyAccepted' }
  | { status: 'alreadyMember' }
  | { status: 'userAlreadyExists' }
  | { status: 'userNotFound' }
  | { status: 'emailMismatch' };
```

Acceptance should run in one Prisma transaction:

```txt
find invitation by tokenHash including tenant
  -> require PENDING, acceptedAt null, revokedAt null, expiresAt > now
  -> find/create user for invited email
  -> ensure no existing tenant membership
  -> create TenantMembership(userId, tenantId, role)
  -> update TeamInvitation to ACCEPTED with acceptedAt
```

Use `updateMany` preconditions for the invitation update:

```ts
where: {
  id: invitation.id,
  status: TeamInvitationStatus.PENDING,
  acceptedAt: null,
  revokedAt: null,
  expiresAt: { gt: now }
}
```

This preserves race safety if two accept attempts happen at the same time.

## Session behavior

After acceptance, generate auth tokens the same way as login/register:

- `TokenService.signAccessToken({ sub, email })`
- `TokenService.generateRefreshToken()`
- persist refresh token hash through `REFRESH_TOKEN_REPOSITORY`
- `TokenService.setAuthCookies(response, accessToken, refreshToken)` in the controller
- return `MeResponse` with all memberships from `MembershipsRepository.findManyByUserId(user.id)`

App-new should then choose the invited membership and set it as selected tenant before redirecting.

Recommended redirect:

```txt
/dashboard
```

## App-new architecture

Add a public page:

```txt
viewpro-app/apps/app-new/src/app/team-invitations/[token]/page.tsx
```

Use the owner invitation route as the page pattern:

- `robots: { index: false, follow: false }`
- render a client acceptance view
- keep visible UI copy in Spanish

Add a feature folder:

```txt
viewpro-app/apps/app-new/src/features/team-invitations/
  api/types.ts
  api/service.ts
  components/team-invitation-acceptance-view.tsx
```

Use direct backend API calls via `apiRequest()`, like owner invitations. Do not add an app-new BFF route unless cookie/tenant proxying becomes necessary. Public token endpoints do not need selected-tenant headers.

### UI behavior

On load:

1. Fetch `GET /team-invitations/:token`.
2. Try `getSessionWithRefresh()` in parallel or after metadata load.
3. Determine which card to show:
   - invalid/expired/revoked/accepted error card;
   - register form if `emailRegistered === false`;
   - already-logged-in same-email accept card if session email matches invitation email;
   - existing-user password form if `emailRegistered === true` and no matching session;
   - wrong-session warning if logged in with another email.

On success:

1. Store/select the invited tenant locally using existing selected-tenant storage conventions.
2. `router.push('/dashboard')`.
3. `router.refresh()`.

## Error handling

Backend error mapping:

| Condition | HTTP |
|---|---:|
| Unknown token | 404 |
| Expired/revoked/already accepted | 410 |
| Invalid DTO/password/session | 400 or 401 |
| Existing same-tenant membership | 409 |
| Logged-in user email mismatch | 403 |

Frontend copy should avoid leaking internals and remain action-oriented:

- invalid: ask for a new link;
- expired: ask the manager to resend;
- already accepted: sign in;
- wrong account: sign out and use the invited email;
- existing user password failure: generic invalid credentials message.

## Security considerations

- Never persist raw invitation tokens.
- Never return token hashes.
- Do not include raw tokens in generic auth redirect query params.
- Public accept endpoint must use `AuthThrottlerGuard` and the configured register/login rate limit.
- Validate all DTO inputs with class-validator.
- Verify existing-user password with the same `PASSWORD_HASHER` used by login.
- Require email equality for current-session acceptance.
- Keep tenant scoping inside the transactional repository mutation.
- Handle Prisma unique membership conflicts as conflict/not available, not 500s.
- Set `robots: { index: false, follow: false }` on the public app page.

## Testing strategy

Backend unit tests:

- validate returns safe metadata for pending invitation;
- validate maps unknown/expired/revoked/accepted tokens safely;
- register mode creates user + membership + accepted invitation;
- register mode rejects existing user;
- login mode verifies existing password and creates membership;
- login mode rejects invalid password;
- current-session mode accepts matching user;
- current-session mode rejects missing/wrong user;
- all modes reject already-member and stale invitations.

Backend e2e tests:

- public validate does not require auth;
- public accept sets auth cookies;
- accepted session includes the invited tenant membership;
- stale/expired/revoked/already accepted links return expected statuses;
- wrong-email authenticated session cannot accept.

App-new tests:

- service validates and accepts through direct backend API paths;
- page renders noindex route shell;
- acceptance view shows register flow for new email;
- acceptance view shows same-session accept flow;
- acceptance view shows password flow for existing users;
- wrong account and stale link states show Spanish error copy;
- success selects invited tenant and redirects to `/dashboard`.

## Acceptance criteria

- A brand-new invited user can accept a team invitation and enter the app as a member of the invited tenant.
- An existing global user with no membership in the tenant can accept the invitation.
- Existing users can accept either from a matching active session or by entering their password on the invite page.
- Users cannot accept invitations for another email.
- Existing same-tenant members cannot consume invitations again.
- Public acceptance never exposes raw tokens or token hashes.
- Invitation acceptance is transactional and race-safe.
- The app redirects to `/dashboard` with the invited tenant selected.
