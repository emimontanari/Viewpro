# Design: ZonaProp property import (#456)

**Status: ACCEPTED (2026-10-04).** The user accepted this design, including the durable work-row strategy and the numeric limits below (codes, TTLs, attempts, image limits, 30-day raw payload retention). Items listed under "Risks and unresolved design validation" are verified during implementation, not re-decided. Source inventory appears in `exploration.md`; unverified integrations are called out there.

## Components and persisted records

Add tenant-owned `PropertyImportBatch`, `PropertyImportCandidate`, and `PropertyImportWork` records, registered in tenant-isolation registry. Batch binds trusted tenant, initiating user, canonical URL, publisher ID, immutable actor build, active run/dataset, expected/discovered/unique-received counts, truncation reason, timestamps and state. Candidate keeps minimal source snapshot for remapping, source ID/URL, mapped editable fields, candidate state (`ready`, `existing`, `incomplete`, `rejected`, `confirmed`, `imported`/`failed`), errors, selected/excluded decision, and resulting reference. `ExternalPropertyReference` has unique `(tenantId, externalSource, externalId)` and a relation to engagement. Publisher claim has `(externalSource,publisherId)`, tenant, lifecycle/audit; enforce global uniqueness only for approved claims, with transactional conflict protection and explicit approve/reject/revoke/transfer contract operations. Pending claims are non-exclusive.

Work rows carry kind, state, attempts, lease/claimed_at, last_error, idempotency key and safe correlation identifiers. Store no secret in rows. Startup resumes non-terminal work; webhook receipt, confirmation and explicit retry trigger work. Lease expiry permits recovery; no timer or polling loop. Durable transitions are idempotent; only pending candidates are retried.

## Trust boundaries and publisher proof

Accept HTTPS canonical ZonaProp advertiser URLs only; reject unexpected host, credentials, malformed path and unrecognized slug. Resolve publisher ID server-side, bind tenant/user/batch server-side, and never accept those IDs from browser parameters. Fetches use allowlisted hosts and redirect revalidation. Parse the provider-published `agencyEmail`; normalized domain equality with a verified active same-tenant `PRINCIPAL_MANAGER` email is context signal only, never proof or approval. Every claim requires a random one-time code sent to the exact trusted published address; fallback is a short random code placed in a publisher listing description and verified via one bounded single-listing scrape. Propose 8-digit codes, email TTL 15 minutes, listing-code TTL 24 hours, five attempts per challenge, resend cooldown 60 seconds and maximum three sends/hour per tenant+publisher/address; hash codes with keyed HMAC and constant-time comparison, never log them. Audit issuer, method, timestamps, outcomes, throttles and actor. These numeric limits are accepted. Name/phone never prove identity or control. Approved-claim conflict returns a non-disclosing contact-support result; no manual operator review or new provider/identity integration.

## Apify and completeness

Use `apify/web-fetch` with `formats:["links"]` to discover slug-bearing `/propiedades/clasificado/` URLs, page through until reported total, deduplicate URL/ID, then `memo23/zonaprop-scraper` with discovered URLs. Pin actor build per batch/run. Set actor-native `maxItems`, `maxTotalChargeUsd`, bounded concurrency and retry counts; ignore `callOptions.maxItems`. Secret stays server-side. Webhook validates secret, responds quickly, and schedules durable work; accept only a run and dataset pre-bound to batch, reject stale/duplicate/out-of-order run updates. Never trust webhook-supplied tenant/publisher/dataset to select data. Persist expectedCount, discovered count, unique results, and explicit truncation reason. Zero results, first-page-only, unexplained count mismatch, charge/item cap, stale run or malformed payload is incomplete/failed, never silently complete. Preserve already valid candidates across retry. Smoke is explicit, authorized, opt-in and bounded by item/cost ceilings; normal tests use fixtures only.

## Mapping, staging and confirmation

Map provider stable feature codes, not display labels; extract numbers with units. Parse Córdoba three-part and CABA two-part locations; address from streetAddress; postal code is not fallback. Use root `realEstateType`/`posting.real_estate_type`; unknown types map `OTHER`; temporary rental maps `RENT`. Validate numeric ranges, positive/valid price and currency as a pair, supported currency, and safe integer conversion to `publishedPriceCents` (verify Prisma integer width before code). Result publisher must equal URL publisher or reject candidate with operational evidence. Preserve source snapshot with defined retention and deletion schedule; minimize contact/raw data.

Staging creates no asset, engagement or image. Existing reference is `existing`; six required fields are editable; missing values yield `incomplete`; bad source/mapping yields `rejected`. UI shows processing/completeness plus ready/existing/incomplete/rejected and row reasons, selection and field correction. Confirmation revalidates actor membership/permission and publisher claim, then handles selected ready rows independently through the established engagement creation/capacity semantics. Idempotent uniqueness handles concurrent confirmations; existing references never duplicate. Capacity failure is explicit/retryable with no false complete state; partial retry only pending candidates. Attribute `createdBy`/`uploadedBy` to authorized initiating actor; webhook has no implicit authority. Share canonical create/capacity path (`createWithAsset`, `active-property-engagement-capacity.ts`, `canonical-property-materializer.ts`) rather than duplicate business rules.

## Images and UI

After confirmation, durable per-image work copies remote images to R2 using deterministic keys. SSRF controls: HTTPS only, strict source-host allowlist, validate every redirect and DNS/IP to block loopback/private/link-local/reserved ranges, re-resolve safely against rebinding, bounded redirects/timeouts, image MIME allowlist and signature check, per-image byte cap, total batch byte cap and count cap. Never trust content-length; stream with hard byte ceiling. Accepted limits: 10 images/property, 10 MiB/image, 50 MiB/property, 3 redirects. Persist each outcome; retries are idempotent and do not duplicate property/image keys. UI differentiates property imported, image copy pending/partial/completed, and failure/retry.

UI requires URL entry, verification/code steps, progress, exception review and editable six fields, selection/exclusion, confirm, row/batch outcomes, capacity retry and explicit no-owner notice with #459 handoff. Tenant BFF follows existing `bff-api.ts` convention; backend remains authorization authority.

## Secrets, retention, operations

Add explicit env-schema configuration and production guards for Apify token/webhook secret, challenge HMAC key, and R2 use of existing storage configuration; never expose secrets to browser/logs/errors. Store only minimum payload snapshot; raw provider payload max retention is 30 days (accepted); challenge/audit metadata follows existing retention policy, verified during implementation. Coordinate additive migration timing/lock duration with pending Neon migrations; do not assume deployment order or run migration without ops approval. Add tenant registry parity tests, Córdoba/CABA fixtures and offline contract tests. Apify smoke is not a normal test.

## Risks and unresolved design validation

Verify platform-control guard/service-token mechanism before choosing webhook authentication integration. Confirm integer storage width, existing email sender constraints, tenant isolation registration expectations, R2 fetch/storage capabilities and allowed-host policy, active engagement creation's image and attribution semantics, and Neon migration schedule. Code/byte/cost limits, data retention, retry/backoff values, Apify actor pin, concurrency, UI permission matrix and precise capacity retry response require explicit acceptance or evidence. Domain equality is not a security boundary; no generic-domain denylist is used. No unverified integration should be represented as existing capability.
